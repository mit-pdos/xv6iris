# kernel-rocq — the xv6 kernel ELF image as Rocq definitions

Auto-generated by `../tools/dump_elf.py` from `../xv6-riscv/kernel/kernel`
(the built xv6 ELF). Rocq port of the Lean `KernelInstrs`/`KernelData`/`KernelSyms`
files from the previous iteration. Standalone: depends only on Coq's
`List`/`ZArith`/`String` (no coq-sail-stdpp / iris), so it compiles fast and
independently. Logical name `Kernel` (`_CoqProject`: `-R . Kernel`).

Built/verified on the project-local opam switch (Rocq 9.0.1):
```
eval $(opam env --switch=/shared/xv6rocq)
cd kernel-rocq && coqc -R . Kernel KernelInstrs.v   # ~11 s
                  coqc -R . Kernel KernelData.v     # ~3 s  (Requires Kernel.KernelInstrs)
                  coqc -R . Kernel KernelSyms.v     # ~0.6 s
```

## Files

### `KernelInstrs.v` — code (`--format rocq`)
```coq
Record kinstr := MkKInstr { ki_addr : Z; ki_width : nat; ki_enc : Z; ki_asm : string }.
Definition kernel_instrs : list kinstr := List.concat [ kernel_instrs_chunk0; ... ].
```
8423 instructions, address range `0x80000000 .. 0x800053d6`. `ki_enc` is exactly
the little-endian integer the Sail RISC-V fetch assembles from the bytes — i.e.
the value to feed `encdec_backwards` / `encdec_compressed_backwards`. `ki_asm`
is the objdump disassembly (humans only). Symbol headers from objdump are kept
as `(* <name> @ 0x... *)` comments inline.

### `KernelData.v` — data + image extent (`--format rocq-data`)
```coq
Definition kernelMemBase : Z := 0x80000000%Z.   (* lowest loadable vaddr *)
Definition kernelMemEnd   : Z := 0x80023528%Z.   (* vaddr + memsz, INCLUDING .bss *)
Definition kernel_data : list kinstr := List.concat [ kernel_data_chunk0; ... ].
```
2277 words. `kernel_data` is every byte of the PT_LOAD image **not** covered by a
dumped instruction (grouped into 8-byte words where aligned, stray bytes solo;
`ki_width` is the width in bits, `ki_enc` the value, `ki_asm = ""`). Reuses the
`kinstr` record from `Kernel.KernelInstrs`.

### `KernelSyms.v` — symbol table (`--format rocq-syms`)
```coq
Definition kernel_symbols : list (string * Z) := List.concat [ kernel_symbols_chunk0; ... ].
Definition sym (q : string) : Z := (* find by name, 0 if absent *).
```
222 symbols (from `nm`, sorted by address). Use `sym "main"%string` (= `0x80000e82`)
in theorem statements/proofs to name addresses instead of hard-coding them.
Verified: `sym "main" = 0x80000e82`, `sym "scheduler" = 0x80001d78`,
`sym "kinit" = 0x80000aec`, `sym "absent" = 0`.

## The full initial memory (code + data + BSS)

- **Loaded bytes** = `kernel_instrs` (code) ∪ `kernel_data` (data) — together the
  complete on-disk PT_LOAD image, byte-for-byte (zero bytes inside the image are
  kept; the Sail model faults on reads of unmapped memory).
- **BSS / zero-init** = `[kernelMemBase, kernelMemEnd)` minus the loaded byte
  addresses. The kernel's `.bss` is zero at boot; it is the part of the image
  extent (`vaddr + memsz`) beyond the on-disk bytes (`vaddr + filesz`).

So the initial memory is: every address in `[kernelMemBase, kernelMemEnd)` holds
`0`, then overlaid with the bytes of `kernel_instrs` (split into `ki_width/8`
little-endian bytes from `ki_enc`) and `kernel_data`.

## Chunking

`kernel_instrs` / `kernel_data` / `kernel_symbols` are emitted as `_chunkN`
definitions of ≤ 200 entries each and joined with `List.concat`, because Coq
elaborates a single huge list literal in time super-linear in its length (deeply
nested `cons`). Same reason the Lean emitters chunk.

## Future glue (NOT built here)

To feed the iris model's `mem : gmap Arch.pa (bv 8)` (`/shared/xv6rocq/iris/`):
fold a zeroed `[kernelMemBase, kernelMemEnd)` and overlay each `kinstr`'s
`ki_width/8` little-endian bytes (from `kernel_instrs ++ kernel_data`) into the
gmap. Deliberately left as a separate step so these files stay standalone and
dependency-free.
