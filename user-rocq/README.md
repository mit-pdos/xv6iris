# user-rocq — xv6 USER-SPACE program images as Rocq definitions

Auto-generated by `../tools/dump_elf.py` from the ELFs the xv6 build links in
`../xv6-riscv/user/` (`make -C xv6-riscv fs.img`). Same shape as
[`../kernel-rocq/`](../kernel-rocq/README.md) — this is the *same dumper*, run
with a different `--prefix` — but for the programs the kernel `exec()`s.
Standalone: depends only on `List`/`ZArith` and stdpp's `gmap`/`bitvector`, so
it compiles in seconds and independently of `iris/`. Logical name `User`
(`_CoqProject`: `-R . User`).

```
make dump          # (re)dump + compile;  make user-rocq compiles only this dir
make dump-force    # re-dump even if make thinks the .v are current
```

Currently dumped: **`sync`** (`user/_sync`, from `user/sync.c`: `sync(); exit(0)`).
To add a program, add a `<prog>:<Module>` pair to `USER_DUMPS` in the top-level
`Makefile` and list its three files in `_CoqProject`.

## What is different about a user image

The dumper is ELF-generic, but a user program is not laid out like the kernel,
and the proofs have to know it:

- **It is linked at virtual address 0** (`user/user.ld`: `. = 0x0;`), not at
  `0x80000000`. So `syncMemBase = 0x0`, and page 0 of the process page table is
  the program's first text page. Addresses in this module are *user virtual*
  addresses in a per-process page table — they are only meaningful together
  with the process whose `satp` maps them, and they deliberately do not overlap
  the kernel's names (`sync_bytes` vs `kernel_bytes`).
- **The entry pc is not the lowest text address.** `syncEntry = 0x12` is
  `SyncSyms.start` (`user/usys.S`), while `SyncSyms.main = 0x0`. `exec()` puts
  the entry in the trapframe's `epc`; `start` calls `main` and then `exit`.
- **There are two PT_LOAD segments**, not one: `R-X` text+rodata at 0, and an
  `RW-` segment at 0x1000 with `filesz = 0` and `memsz = 0x20` — a pure `.bss`
  that contributes no on-disk bytes but must be mapped and zeroed.
  `sync_segments` is that table, which is exactly what `exec()` walks.

## Files (for `sync`)

### `SyncInstrs.v` — the text image (`--format rocq`)
```coq
Definition sync_bytes : gmap Z (bv 8) := list_to_map [ ... ].   (* 2240 bytes *)
Record kinstr := MkKInstr { ki_addr : Z; ki_width : nat; ki_enc : Z }.
Definition sync_instrs : gmap Z kinstr := list_to_map [ ... ].  (* 842 instrs *)
```
`sync_bytes` maps each byte ADDRESS to its VALUE, so fetching an instruction at
`pc` is `W` consecutive lookups regardless of RVC/32-bit width or alignment.
`sync_instrs` is the decode INDEX (keyed by instruction number in program
order): it names the i-th instruction's `(addr, width, enc)` so a proof can pick
the right decode lemma. `ki_enc` is exactly the little-endian integer the Sail
model's fetch assembles — the value for `encdec_backwards` /
`encdec_compressed_backwards`. Both maps are `Typeclasses Opaque` (forcing a
20k-entry `list_to_map` during typeclass resolution costs minutes). The `kinstr`
record carries no image-specific data and is deliberately spelled the same in
every dump, so a re-dump never rewrites thousands of entries just to rename it;
a file that Requires two dumps qualifies (`User.SyncInstrs.kinstr`).

### `SyncData.v` — everything else that is loaded (`--format rocq-data`)
```coq
Definition syncMemBase  : Z := 0x0.      (* lowest PT_LOAD vaddr            *)
Definition syncMemEnd   : Z := 0x1020.   (* max vaddr+memsz, INCLUDING .bss *)
Definition syncEntry    : Z := 0x12.     (* ELF entry pc = SyncSyms.start   *)
Definition sync_segments : list (Z * Z * Z * Z) := [ ... ].  (* vaddr,filesz,memsz,flags *)
Definition sync_data    : gmap Z (bv 8) := list_to_map [ ... ].  (* 1156 bytes *)
```
`sync_data` is every loadable byte *not* covered by an instruction (here:
`.rodata` and `.eh_frame`, `0x8c0 .. 0xd44`), per-byte like the code. Segment
flags are `PF_X 1 | PF_W 2 | PF_R 4`.

### `SyncSyms.v` — the symbol table (`--format rocq-syms`)
One `Definition <sym> : Z` per `nm` symbol (47 of them), so a spec says
`SyncSyms.main` / `SyncSyms.sync` instead of a magic constant. The module
namespace is what keeps `SyncSyms.strlen` and `KernelSyms.strlen` apart.

### `SyncElfRaw.v` — the whole debug-stripped ELF (`--format rocq-raw`)
```coq
Definition sync_elf_hex : PrimString.string := List.fold_left PrimString.cat [ sync_elf_hex_chunk0; ... ] ""%pstring.
Definition sync_elf_size : Z := 10960%Z.
```
Same shape as [`../kernel-rocq/KernelElfRaw.v`](../kernel-rocq/README.md): the
whole debug-stripped ELF, hex-encoded as one Rocq 9 `PrimString.string`,
chunked at 8192 hex chars/chunk and joined with `List.fold_left PrimString.cat`
— the ground truth `iris/ElfFile.v`'s general ELF64 semantics get instantiated
against, as opposed to `SyncInstrs.v`/`SyncData.v` above, which are already
split into code/data by this dumper's own (fallible) reasoning. Every dumped
program gets one (`EchoElfRaw.v`, `ShElfRaw.v`, `InitElfRaw.v`), each with its
own `<prefix>_elf_hex` / `<prefix>_elf_size`.

## The initial process image

Everything in `[syncMemBase, syncMemEnd)` is zero, overlaid with the bytes of
`sync_bytes` (code) and `sync_data` (data) — together exactly the on-disk
PT_LOAD image, byte for byte, with zero bytes inside the image kept. The
`.bss` is what is left: in `[MemBase, MemEnd)` but in neither map. Verified for
`sync`: code (2240 bytes) + data (1156) = 3396 = the two segments' `filesz`.

Note that this is the image `exec()` *loads*; a running process also has an
argv/stack page above it, which is not part of the ELF and so not dumped here.
