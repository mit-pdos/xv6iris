# xv6rocq — Reasoning about xv6 execution with the Sail RISC-V semantics

> **Status / which backend to use.** The Rocq path (this file) imports and
> compiles the Sail RISC-V model, but its generated decoder **cannot be reduced**
> to a concrete AST (see `NOTES_decode_reasoning.md`). The project therefore
> moved to **Lean 4**, where a *reduced* executable Sail model actually decodes
> every xv6 kernel instruction to a concrete AST via `#eval`. **Start at
> [`lean/README.md`](lean/README.md).** The Rocq setup below is still valid for
> stating theorems about the model.

## (Rocq backend) Reasoning about xv6 execution with the Sail RISC-V semantics in Rocq

This project sets up the infrastructure to formally reason, in the
[Rocq Prover](https://rocq-prover.org/) (formerly Coq), about the execution of
the [xv6-riscv](https://github.com/mit-pdos/xv6-riscv) kernel
(`kernel/kernel`) on a RISC-V machine, using the official
[Sail RISC-V](https://github.com/riscv/sail-riscv) ISA semantics compiled to
Rocq.

## Build

Everything is driven by the top-level **`Makefile`**, which runs all Rocq
commands inside the project-local opam switch (`/shared/xv6rocq`), so you do
**not** need to `eval $(opam env …)` yourself.

```sh
cd /shared/xv6rocq
make            # == make proofs: build the model, the kernel dump, and all Iris proofs
make proofs     # compile iris/ (and its model + kernel-rocq dependencies)
make model      # compile only model-xv6iris/ (the Sail-generated Coq model)
make kernel     # build the xv6 kernel ELF (xv6-riscv/kernel/kernel)
make dump       # regenerate kernel-rocq/*.v from the ELF, then compile kernel-rocq/
make clean      # remove Coq build artifacts; make distclean also cleans the xv6 tree
```

The build graph: **xv6 kernel ELF** → (`dump_kernel.py`) **`kernel-rocq/*.v`** →
`.vo`; the **Sail model** `model-xv6iris/*.v` → `.vo`; then **`iris/*.v`** →
`.vo` (depending on both). Within each Coq directory, the compile order is
computed automatically by `coq_makefile` from that directory's `_CoqProject`.

Prerequisites already present in this environment: the opam switch (Rocq 9.0.1,
coq-iris 4.4.0, coq-sail-stdpp 0.20.1), `riscv64-linux-gnu-gcc`/`objdump` (for
the kernel + dumper), and `python3`. Override the disassembler with
`make OBJDUMP=…` if needed.

### Regenerating the Sail model

The model `.v` in `model-xv6iris/` are checked in. Regenerating them requires
the **Sail compiler** (`sail` 0.20.1 + `sail_coq_backend`, via opam) and a
clone of [`sail-riscv`](https://github.com/riscv/sail-riscv) at a sibling path
(`../sail-riscv`, or pass a path explicitly). If `sail` isn't on `PATH`,
`make model-gen` just prints this reminder.

```sh
eval $(opam env)   # into whichever switch has `sail` installed
tools/regen_sail_model.sh [path/to/sail-riscv]     # ~10 min, dominated by the Sail->Rocq step
make model
```

The script configures sail-riscv's own cmake project (for its module list and
build deps), then invokes `sail --coq` directly with **this repo's config**
(`model-xv6iris/sail-config-rv64d.json`) instead of sail-riscv's own default
config, compile-checks the output with `coqc`, and installs
`rv64d.v`/`rv64d_types.v`/`riscv_extras.v` into `model-xv6iris/`. (The model is
built with the `--dcoq-undef-axioms` flag, which is why `Print Assumptions`
reports the five `rv64d.*` platform axioms.)

Our config differs from sail-riscv's upstream default in exactly one place:
`platform.simple_interrupt_generator.supported` is `false`. Sail's built-in
SIG test device otherwise claims the MMIO window `[0xC000000, 0xC000020)`,
which collides with xv6's real PLIC base address (`0xC000000`, see
`iris/DevModel.v`'s `plic_base`) — with SIG enabled, the Sail model intercepts
PLIC priority-register accesses for interrupt sources 0–7 internally instead
of routing them to xv6iris's own PLIC model. See the comment at the top of
`model-xv6iris/sail-config-rv64d.json` for why disabling SIG is safe (it only
removes the address-window claim, not the interrupt-pin registers the PLIC
model wires into).

## The Sail RISC-V Rocq semantics

Generated from `sail-riscv` and installed into Rocq's
`user-contrib/Riscv` (logical name `Riscv`) for the `rv64d` configuration:

- `Riscv.rv64d_types` — types, including the decoded-instruction AST `instruction`.
- `Riscv.rv64d` — the model: decode, execute, fetch, CSRs, memory, etc.
- `Riscv.riscv_extras` — handwritten Rocq support used by the model.

Key entry points (all in `Riscv.rv64d`):

| Function                        | Type                          | Meaning                         |
| ------------------------------- | ----------------------------- | ------------------------------- |
| `encdec_backwards`              | `mword 32 -> M instruction`   | decode a 32-bit instruction     |
| `encdec_compressed_backwards`   | `mword 16 -> M instruction`   | decode a 16-bit (RVC) instr.    |
| `execute`                       | `instruction -> M ExecutionResult` | execute one instruction    |
| `fetch`                         | `unit -> M FetchResult`       | fetch from current PC           |

`M` is the Sail free monad; `mword n` is an n-bit vector (`SailStdpp`).

See "Regenerating the Sail model" above for how to rebuild these from
`sail-riscv` — the model is compiled locally in `model-xv6iris/` (via `-R .
Riscv`, see `model-xv6iris/_CoqProject`), not installed into a global
`user-contrib`.

## Dumping the kernel instructions

`tools/dump_kernel.py` disassembles the kernel ELF with `objdump` and emits
`rocq/KernelInstrs.v`. Each instruction becomes a record:

```coq
Record kinstr := MkKInstr {
  ki_addr  : Z;      (* virtual address *)
  ki_width : nat;    (* 16 (RVC) or 32 bits *)
  ki_enc   : Z;      (* instruction word, exactly as Sail fetches it (LE bytes) *)
  ki_asm   : string  (* objdump disassembly, for humans *)
}.
Definition kernel_instrs : list kinstr := [ ... ].   (* 8423 entries *)
```

`ki_enc` is precisely the integer the Sail decoder expects, so no further
byte-swapping is needed.

```sh
python3 tools/dump_kernel.py            # defaults: xv6-riscv/kernel/kernel -> rocq/KernelInstrs.v
python3 tools/dump_kernel.py --help     # options: --kernel --out --objdump --name
```

## Building the Rocq files

```sh
cd rocq
eval $(opam env)
coqc -R . Kernel KernelInstrs.v
coqc -R . Kernel SailBridge.v
```

`SailBridge.v` provides:

```coq
Definition decode32 (enc : Z) : M instruction := encdec_backwards (mword_of_int (len:=32) enc).
Definition decode16 (enc : Z) : M instruction := encdec_compressed_backwards (mword_of_int (len:=16) enc).
Definition decode_kinstr (k : kinstr) : M instruction := ...   (* dispatch on ki_width *)
Definition kernel_decoded : list (M instruction) := map decode_kinstr kernel_instrs.
```

## Next steps for reasoning

- **Decoding to a concrete AST.** `decode32 enc : M instruction` is *definitionally*
  the Sail decode, but do **not** expect `Eval vm_compute`/`native_compute` to
  reduce it: the generated model is ~5 MB of Rocq and full kernel-evaluation
  blows the VM stack / takes minutes to native-compile. Instead, reason
  symbolically — e.g. prove `decode32 enc = returnm <expected-ast>` for specific
  opcodes by `cbn`/`simpl` with targeted `unfold`s of just the relevant
  `encdec_*` clauses, rather than whole-model reduction.
- Model the kernel's memory image (addresses → bytes) and connect `fetch` to
  `KernelInstrs` so the model can step through real kernel code.
- State and prove invariants over sequences of `execute` steps.
